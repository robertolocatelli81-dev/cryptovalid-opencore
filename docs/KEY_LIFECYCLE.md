# Key Lifecycle — OMEGA evidence stack

> **Scope note (2026-09-13).** This document describes the *whole* CryptoValid evidence stack. Only these
> mechanisms live in **this** repository: `verifier.py` (hash-chain/idx/linkage, strict acceptance profile),
> `sigsuite.py` + `ap2_evidence.py` (hybrid ML-DSA-65 co-signature, `verify_producer_block`, pinned
> `trusted_producer_keys`), `verifiers/` (JS/Rust/Swift + `differential_oracle.py`). Mechanisms cited by
> module names that are **not** in this repo — `canonical.py`, `device.py`, `interop/confidential.py`,
> `longterm_evidence.py`, `DeviceTrust`/`OrgTrust`, `ReplayGuard`, `hwkeys.ExternalSigner`,
> `timestamp.verify` — are implemented in the sibling toolkit
> [omega-evidence](https://github.com/robertolocatelli81-dev/omega-evidence) (Apache-2.0) and are listed here
> for completeness of the threat model, not as capabilities of this package.

*Status: 2026-09-03. Every key type, from generation to destruction, as implemented.
Honest-scope: where custody depends on an operator action (offline root, HSM), that is

## 1. Key inventory

| Key | Algorithm | Where it lives | Purpose |
|---|---|---|---|
| **Device signing key** | Ed25519 (software) OR ECDSA-P256 (hardware) | 32-byte seed in a 0600 file, OR in Secure Enclave / StrongBox / HUKS / TPM (never exported) | Signs every envelope / ledger entry. Its SHA-256 is the `device_id`. |
| **Device encryption key** | X25519 | Derived from the Ed25519 seed by domain separation, OR a separate 32-byte `enc_seed` when the signing key is hardware-held (an enclave key cannot be exported to derive from) | Receives encrypted payloads (ECIES-style). |
| **Organisation root** | Ed25519 or ECDSA-P256 | Offline / HSM / KMS — the CA-equivalent | Signs device credentials, policies, revocation lists. |
| **AP2 producer identity** | Ed25519 (classical) + **ML-DSA-65** (FIPS 204, PQ) | PKCS8-DER keyfile, 0600 (or HSM) | Hybrid producer signature over evidence packs (long-term, quantum-durable). |
| **TSA trust anchor** | (external) TSA roots, PEM | Operator-supplied `ca_file` | Verifies RFC 3161 timestamps. |

## 2. Generation

- **Device / producer**: 32-byte CSPRNG seed (`secrets.token_bytes(32)`); an empty/short seed is **rejected**, never silently replaced by a random one (a failed KMS fetch must fail loudly). ML-DSA-65 keys are generated by the vetted `cryptography` library (never home-grown).
- **Hardware**: the private key is generated *inside* the Secure Enclave / StrongBox / HUKS / TPM and never leaves it; the app holds only the public key and calls `ExternalSigner.sign`.
- **Organisation root**: generated once on an admin host that MUST be treated like a CA (offline or HSM-backed).

## 3. Storage

- Software seeds and the producer identity: files with mode **0600** in a **0700** state directory (e.g. `~/.config/cryptovalid`, producer keyfile). No key material in logs, envelopes, or the hash-chain.
- Hardware keys: in the platform keystore; custody is the platform's (attestation available: Android key attestation, App Attest).
- Organisation root: OFFLINE or HSM/KMS. Compromise forges the whole fleet — this is the highest-value secret.

## 4. Distribution & pinning (trust establishment)

- **Peer pairing (small teams)**: the device **card** (id + public keys + fingerprint) is exchanged **out of band** (QR / text / one-time) and PINNED in `DeviceTrust`. A different key under a known id is refused as impersonation.
- **Organisation (fleet, zero-touch)**: the admin enrolls a device — the root signs a **credential** binding {device card, role, keystore class, validity window, posture claims}. The credential travels inside every envelope; any device trusting the root card trusts it. No peer pairing needed.
- **Producer key (AP2)**: the relying party MUST pin the producer public key out of band (`trusted_producer_keys`). An embedded, unpinned producer key proves internal consistency, NOT authenticity.
- **TSA anchor**: the verifier operator supplies the TSA roots (`ca_file`); without them RFC 3161 tokens are recorded but UNVERIFIED.

## 5. Rotation

- **Device**: issue a new credential for the new key with `supersedes = <old serial>`; revoke the old (§6). Manual pairs: re-exchange the card (pinning refuses a silent key swap — deliberate).
- **Algorithm migration** (e.g. add PQ, retire Ed25519 by 2030): the format is crypto-agile — each signature declares its `sig_alg`; register a new backend and re-sign / co-sign. Existing packs stay verifiable (legacy algs still resolve).
- **Producer identity**: create a new `ProducerIdentity`, re-sign new packs; old packs remain valid under the old pinned key + their time anchor.
- **Organisation root rotation**: a NEW root card must be distributed out of band and re-pinned (`OrgTrust.set_root` refuses a silent root-key change) — the most disruptive rotation; plan for it.

## 6. Revocation

- **Device / credential**: the root issues a **signed, sequenced CRL**; verifiers apply it (`OrgTrust.set_crl`), rollback to a lower sequence is refused, and revoked devices are dropped from the cache immediately — every later envelope from them fails at the trust layer. Credentials also carry a hard `not_after`.
- **Manual pair**: `DeviceTrust.remove(device_id)`.
- **Producer key**: rotate (§5) and stop pinning the old key.

## 7. Loss & recovery

- **Lost device**: revoke its credential (CRL) and re-enroll a replacement — no key recovery (keys are per-device; evidence already signed stays valid under the pinned key + time anchor).
- **Lost software seed**: the identity is gone; evidence it signed remains verifiable, but it can no longer sign — re-enroll a new identity.
- **Lost organisation root**: **catastrophic** — no recovery beyond a securely-held offline backup. Without a backup, the entire fleet must be re-rooted (new root card, re-enroll every device). Keep an offline/HSM backup and an M-of-N custody plan.

## 8. Post-quantum transition (timeline-aware)

- **Now**: sign long-retention evidence packs with the **hybrid** block (classical + ML-DSA-65); a pack is `pq_protected` only when a VALID, pinned ML-DSA signature is present. The classical half is a hedge against ML-DSA implementation/algorithm risk — it provides **no** quantum resistance.
- **Durable pre-quantum existence**: a PQ signature protects the PACK; proving a record *existed before* a CRQC still needs a trusted time anchor (RFC 3161 with a PQ/qualified TSA, or RFC 4998 renewal via `longterm_evidence.py`).
- **By 2030 / 2035** (NIST IR 8547): migrate long-retention records to PQ **before** short-lived ones; crypto-agility (`sig_alg`) is the migration mechanism; register SLH-DSA/ML-DSA backends behind the mandatory KAT gate.

## 9. Honest limits

Hardware-key custody is only as strong as the platform's attestation, which the enrollment service MUST verify (the credential records the keystore class as an *asserted* claim). The producer/organisation key hygiene (offline root, HSM, backups, M-of-N) is operational and outside what the code can enforce. The ArkTS hardware path and the on-device Apple path are not yet validated on real devices.
